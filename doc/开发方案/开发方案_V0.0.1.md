# 三国开放世界战棋游戏：开发方案 V0.0.1

- 版本：V0.0.1
- 日期：2026年11月6日
- 规则依据：《战斗方案 V0.0.2》
- 文档定位：确定技术方向、底座筛选方式、首轮适配范围和分阶段验收标准。
- 当前阶段：已完成候选底座初筛、部分源码检查和基础启动检查，尚未完成底座适配试改与最终选型。
- 状态约定：已确定事项、初筛结论、实施建议和待定事项分别标明。本文不将测试公式或候选框架的默认规则转化为正式游戏规则。

## 一、项目目标与开发条件

游戏以三国历史为背景，采用2D像素表现，结合开放探索、角色招募、队伍经营和回合制方格战棋。独行武将与带兵军团可以出现在同一战场；外部单位占一格，发起攻击后进入内部有限交战，再返回外部战场。

开发者游戏开发、编程和美术经验较少，主要依靠AI协助。因此，开发过程中应优先复用合适的通用功能，以小规模、可观察、可复现的结果推进，控制同时引入的系统数量。

本阶段的目标是验证技术承载方式，建立后续战斗开发的可靠基础。开放世界、完整经济和大量三国内容尚不进入首轮实施范围。

| 项目 | 当前口径 | 状态 |
| --- | --- | --- |

Godot 4的采用不代表任意Godot 4项目均可直接运行。正式开发前，需要记录引擎具体版本、候选代码提交和依赖，避免开发中途无计划升级。

本开发方案负责“如何实现与验证”；《战斗方案 V0.0.2》负责“游戏如何运作”。二者如有冲突，应回到规则文档明确处理，不通过代码默认值静默改变玩法。

## 三、开发顺序

本轮确定的推进方向为：

1. 从V0.0.2提取底座必须承载的需求。
2. 筛选候选项目，检查源码、文档、版本、授权与扩展方式。
3. 在候选底座中做一次最小适配试改。
4. 根据试改结果选择底座，并锁定技术版本。
5. 补齐内部交战原型必需规则，逐步实现内部结算。
6. 接通外部行动、内部交战与战损保留，形成完整小循环。
7. 核心循环验证后，再扩展探索、成长、后勤和正式内容。

“先明确验证目标”与“先自行编写完整原型”需要区分。少量规则整理用于判断底座是否适合；地图、寻路、回合和界面不应在选型前整套重写。

## 四、底座筛选标准

### 4.1 优先复用的功能

- 方格地图与坐标管理。
- 单位选中、移动、路径预览和移动范围显示。
- 寻路、占位与地形移动成本。
- 可适配的单位行动管理、基础敌方AI和操作界面。
- 后续适合引入的对话、存档和资源编辑功能。

以上是复用目标，不代表一个底座必须一次性提供全部功能。

### 4.2 必须检查的适配能力

| 检查项 | 与本项目的关系 |
| --- | --- |
| 外部单位能否关联独立军团数据 | 地图上的一个单位需要承载多名武将、多支部队和十二格阵形 |
| 外部行动顺序是否可替换 | 本项目采用各单位依次行动，不直接沿用阵营整体回合 |
| 攻击能否调用自定义交战流程 | 外部一次攻击需要执行多成员内部交战 |
| 结算能否暂停等待玩家输入 | 内部允许逐个手动指定合法目标 |
| 数据是否独立于临时场景 | 返回地图或再次交战不能重置兵力、伤势与归属 |
| 结算与动画是否可以分别调整 | 需要逐步实现速度、反击和待机等规则，并查看中间结果 |
| 代码和依赖是否易于理解维护 | 适合开发者与AI共同定位错误、修改和验收 |
| 代码与美术授权是否分别明确 | 避免把演示资源默认带入正式项目 |

不能仅凭演示效果、功能数量或项目关注度判断适配价值。底座提供独立战斗画面，也不等于能够替换为本项目的内部结算。

## 五、候选项目与本轮初筛

| 候选 | 已查明的功能或定位 | 主要适配问题 | 本轮结论 |
| --- | --- | --- | --- |
| GDQuest Tactical RPG Movement | 2D方格移动、选择、范围、路径预览和移动确认/取消；仓库含godot4目录 | 主要是移动示例，缺少完整回合与战斗系统；需要兼容修整 | 优先作为外部地图操作模块试改 |
| aroelke/Godot TBS Framework | C#战棋框架，包含阵营、AI、地图目标和战斗表现接口 | 默认阵营回合；预先计算战斗结果；需要适配数据、回合与结算流程 | 保留为完整框架备选 |
| ramaureirac/Godot Tactical RPG | 方格移动、攻击、基础AI、镜头与控制器支持 | 使用3D结构，与2D方向存在额外转换工作；作者定位为简单模板 | 当前不优先 |
| Ma-Ko-dev/Turn-Based-Prototype | 2D寻路、地形成本、单位行动队列、资源化属性 | 带有较多桌游属性和装备规则；仍为原型项目；有额外授权声明需要核对 | 作为参考，不直接选为主底座 |

补充参考：GDQuest Open RPG定位为传统回合制RPG教学演示，作者明确不以构建框架为目标。现阶段不把它当作已验证的战棋主底座，后续可按需研究外围系统。

### 5.1 优先试改GDQuest移动示例的理由

本项目的特色集中在军团数据、内部交战和外部单位行动方式。轻量移动示例可以提供已有地图操作，同时减少需要拆除的既有战斗假设。

这一判断是待验证的工程建议，不代表已证明轻量示例一定比完整框架省工。其缺少回合与战斗系统，也意味着后续存在明确的自定义开发工作。

### 5.2 C#框架的关键限制

Godot TBS Framework文档中的Army主要组织阵营及其地图单位，不能直接理解为本项目“占一格、包含多个内部成员”的军团。

该框架默认轮转各Army的回合，并在战斗表现之前计算结果。因此，仅替换CombatScene画面不足以支持本项目的手动选敌、状态变化与内部行动流程。若采用，需要评估核心逻辑改造成本，不能将画面接口视为已完成的结算接口。

## 七、首轮底座适配验证

### 7.1 目标

用最少的改动验证：现成外部地图功能能否承载独立军团数据，并完成一次进入交战、修改成员状态、返回地图的过程。

首轮优先在GDQuest移动示例中试改。此阶段不要求实现完整V0.0.2规则，也不将测试扣兵方式当作伤害公式。

### 7.2 最小范围

1. 保留原有单位选择、路径预览与移动能力。
2. 放置双方各一个外部单位，各关联一份独立军团数据。
3. 每个军团先配置少量内部成员；数据结构预留三将八部队、十二格阵形和指挥归属的表达能力。
4. 提供一个明确的测试入口，选定对手后进入简单交战界面。
5. 在界面中修改指定成员的测试兵力或伤势，返回地图。
6. 再次进入交战，检查状态与身份是否保留。

测试入口的接敌距离、测试兵力变化及操作按钮只是验证工具，不构成正式外部攻击或伤害规则。

### 7.3 验收标准

| 编号 | 验收内容 |
| --- | --- |
| A1 | 地图单位仍可正常选择和移动，路径显示与实际移动相符 |
| A2 | 双方军团与各内部成员有独立身份，修改一方不影响另一方 |
| A3 | 进入交战后，外部输入受到正确控制，不会同时移动或重复发起交战 |
| A4 | 返回地图后，原单位位置和军团数据正确保留 |
| A5 | 再次交战时，之前修改的兵力和伤势未被初始配置覆盖 |
| A6 | 可以表达内部位置、成员类型及部队指挥归属 |
| A7 | 未通过把所有成员压成一条军团生命值来绕过数据需求 |
| A8 | 修改范围可说明，关键流程可定位，没有为接入军团而大面积重写地图功能 |

首轮不加入复杂技能、完整伤亡分类、正式美术、动画、探索和后勤。

### 7.4 通过与转向条件

若验收通过，记录仍需修整的问题及预计新增系统，继续比较总体工作量后确定底座。若需要大面积重写地图和单位管理，或状态往返持续不可靠，应暂停扩展，评估C#备选框架的适配成本。

不因已投入少量试改就自动坚持某个项目，也不因首次出现可修复的兼容错误立即弃用。

## 八、底座确定后的阶段计划

以下为开发建议，具体范围可根据适配结果修订；不承诺固定完成日期。

| 阶段 | 核心工作 | 阶段验收 |
| --- | --- | --- |
| P0：底座适配 | 完成第七节验证，比较改造成本，锁定版本与来源 | 能运行、能往返、成员状态独立，明确采用或淘汰理由 |
| P1：内部交战测试台 | 十二格阵形、速度排序、射程、保护、攻击反击和待机 | 逐步执行可观察，关键规则正确且能终止 |
| P2：外部战斗循环 | 明确并实现外部单位排序、行动额度、移动接敌、胜负及退出 | 多个外部单位能够完成一场小规模战斗 |
| P3：持续状态 | 武将失能影响、无兵编组、伤兵阵亡、基础战后保留与存取 | 行动恢复不治疗，战损跨交战和存取仍正确 |
| P4：探索衔接 | 探索触发独立战场、返回探索、基础招募与编组调整 | 形成可反复运行的探索—战斗—战后处理循环 |
| P5：内容扩展 | 正式兵种、技能、成长、装备、后勤及三国内容 | 根据核心循环反馈逐项加入并验收 |

前期可以先验证内存中的状态保留；正式存档属于后续持续状态阶段，不将二者混为一谈。

## 九、P1前需要明确的规则

底座试改可以使用明确标注的测试条件；进入正式内部交战实现前，需要补齐以下缺口：

- 哪些成员构成阻挡，失能或零可战斗兵力后是否占位、阻挡。
- 有合法目标时能否主动待机，能否放弃行动。
- 交战中速度变化是否重排，以及同速随机如何复现。
- 原型所需的最小属性、伤害与兵力计算方式。
- 首版自动选敌优先级，以及手动与自动的操作边界。

技能、范围攻击、穿透绕后、完整叠加规则等可随对应功能逐步明确，不要求为了首轮底座试改全部定案。

P1应重点覆盖V0.0.2已有规则：射程277不能攻击距离300、499不能攻击500；横向列差影响距离；同列保护；受击后反击并消耗行动；待机成员在保护突破后优先重返；无合法行动能够结束；新交战恢复行动但不恢复战损。

P2还需专门观察：内部行动每次交战恢复，会使同一军团面对多个外部敌军时获得多次潜在反击机会。应验证这一既定规则与外部行动设计结合后的效果。

## 十、实施与协作建议

1. 使用Git记录可运行基线、底座来源、每次适配和验收结果；选定底座时固定提交，不直接跟随上游滚动更新。
2. 军团和成员的持续状态由明确的数据对象管理；临时交战界面负责展示与输入，不重新生成并覆盖战损。
3. 外部单位行动与内部成员行动分别管理，不因现成框架的命名或回合机制相似而共用一套额度。
4. 以占位图、文本日志、合法目标提示和逐步执行验证规则，核心流程稳定后再投入动画与正式美术。
5. 对排序、射程、行动消耗和待机终止等关键结算做可重复检查；不以单次“启动没有崩溃”替代玩法验收。
6. 每轮由开发者检查操作结果与战斗日志，AI负责协助实现和排错；出现不明确规则时记录为待定，不静默补成正式设定。
7. 暂不额外叠加大量插件。数据编辑、对话、存档等工具在有具体需求时再评估。
